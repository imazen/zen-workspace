# `zen*` — cross-workspace signal-to-noise tools

Nine commands that answer the questions this workspace asks twenty times a day,
and that encode the specific ways those questions get answered *wrong*.

They are one Python file (`bin/zen`, stdlib only) with `argv[0]` symlinks, so
`zenci` and `zen ci` are the same program. No build step, no dependencies
beyond `gh` + `git` (+ `jj` where present). That matters because the same tree
gets worked on from an aarch64 Mac, a Linux workstation and remote boxes —
a Rust binary would need compiling on each one, and macOS still ships bash 3.2,
which rules out portable shell with associative arrays, `mapfile`, or a single
`stat` invocation that works on both platforms.

## Install

```sh
export PATH="$HOME/work/zen-workspace/bin:$PATH"
export ZEN_AGENT="claude-<something-stable-per-session>"   # used by claim/release/markers
```

`ZEN_AGENT` defaults to `claude-<hostname>`, which is fine for a human and
wrong for two concurrent agents on one box — set it per session.

Repos are discovered generically: anything under `~/work` or `~/work/zen` with
a `.git` or `.jj`. Override with `ZEN_ROOTS=/a:/b`. Roots and the
owner-org list come from `Superwork.toml`, so there is one source of truth.
By default only repos owned by `imazen`/`lilith` are scanned; `--all` adds
forks and upstreams.

Every command takes `-h`.

## The commands

### `zenci [repo…]` — one line per workflow, with a real verdict

```
$ zenci garb zenmetrics
garb        Benchmarks   FAIL   8e2d8960  11 jobs: 3✗ 8✓   first fail: bench (Windows aarch64) › Run benchmarks
garb        CI           FAIL   8e2d8960  12 jobs: 1✗ 11✓  first fail: clippy + fmt › Run cargo clippy --all-features
zenmetrics  CI           FAIL   7e4695b3  11 jobs: 9✗ 1✓ 1-  first fail: Lint (clippy + fmt) › Format check
zenmetrics  Fleet-tooling guard    PASS   7e4695b3  9m ago
```

`--since <rev>` answers the question that a bare run list cannot:

```
$ zenci zenmetrics --since b5b4b27f
zenmetrics  CI                  CANCEL b5b4b27f  no verdict, BUT a job really failed: Lint (clippy + fmt) › Format check
zenmetrics  Fleet-tooling guard PASS   b5b4b27f  1h14m ago
zenmetrics  Job-worker fleet image  NO RUN for b5b4b27f — path-filtered, or superseded before dispatch
```

`--fail-only`, `--branch <b>`, `--fresh`, `--limit N`, `--include-bots`.

Cold across 73 repos: ~16 s. Warm (45 s run cache): ~1 s.

### `zenred [repo…]` — what is broken right now, and who broke it

```
$ zenred
● garb  (main)  imazen/garb
    CI  8e2d8960  22h31m ago
      first real failure: clippy + fmt › Run cargo clippy --all-features -- -D warnings   (12 jobs: 1✗ 11✓)
      │ error: using `chunks_exact_mut` with a constant chunk size
      broke at: fa31c3af bench: garb's first per-kernel tier benchmark; cross-bpp rejection re-verified
      last green: 67c4efb6 33d ago bench: re-measure cross-bpp at REAL row granularity
      https://github.com/imazen/garb/actions/runs/33271823594
● zenmetrics  (master)  imazen/zenmetrics
    CI  affcee66  1h13m ago   [newer runs exist but were cancelled/are running — no verdict since]
      first real failure: Compile (ubuntu-latest) › Run fleet-orchestration tests   (11 jobs: 9✗ 1✓ 1-)
      │ error: failed to load manifest for workspace member `…/crates/zenfleet-va…`
```

That second entry is the whole reason this command exists: a workspace member
path-deps a sibling that CI never clones, so it builds locally and fails
everywhere. It was found forty minutes late, by accident, while looking at
something else. `zenred` finds it in fifteen seconds across the whole tree.

`--no-log` skips log fetching (fast, loses the error line). `--limit N` widens
the blame window. Exit status is 1 when anything is red, so it composes.

### `zenpushed <rev> [repo]` — is it on the trunk?

```
$ zenpushed @
NOT ON TRUNK 713afe5be6ff feat(tools): cross-workspace zen* CLI tooling
  zen-workspace/main is at 6fe6f6730ef6
  origin/main was last updated 1d ago locally — re-run with --fetch before believing this
  advance the bookmark:  jj bookmark set main -r @- && jj git push --bookmark main
  `jj git push --change @-` pushes to an autogenerated push-* bookmark, NOT main
```

"Pushed" and "on the trunk" are different facts. A session once lost fourteen
hours to that gap, because `jj git push --change @-` puts commits on an
autogenerated `push-*` bookmark and nothing ever moved `main` to them. Exit
status is the answer, so this drops straight into a script.

### `zenverify [rev]` — the post-push checklist

```
$ zenverify 682b266            # a real commit from the incident
zenjxl  682b26643545  (trunk: main)
  ✓ has a description            docs(changelog): record the third-party dependency pass and its no-op result
  ✗ is NON-EMPTY                 EMPTY COMMIT — you probably edited before `jj new`; the edits are in the parent change
  ✓ is on origin/main            origin/main @ 4372d8a8735f
VERIFY FAILED
```

Defaults to `@-` in a jj repo, `HEAD` otherwise. `--expect <glob>` (repeatable)
asserts the commit actually touches what you think it touches. `--fetch`
refreshes origin first.

### `zenclaim` / `zenrelease` / `zenmarkers` — the `.workongoing` protocol as verbs

```
$ zenclaim -m "wiring CLL into the zenjxl decoder"
CLAIMED zenjxl  2026-08-30T18:17:09Z claude-cli-tools wiring CLL into the zenjxl decoder

$ zenclaim jxl-encoder -m "trying to barge in"
REFUSED — jxl-encoder is claimed by claude-T2-secant-guard (3m ago)
  watching CI 33326018764
  pick another repo, or wait; --force overrides (do not)

$ zenmarkers
LIVE       zen-workspace        1s     claude-cli-tools       claimed 1s ago — back off
STALE+WORK jxl-encoder          6m     claude-T2-secant-guard 1 file(s) modified in @: M CLAUDE.md → do NOT clobber
PAUSED     rav1d-safe--fuzzgate 16d    claude-fuzzgate-agent  deliberate pause, left for the next agent
```

`zenclaim` refuses two ways: a *fresh* marker owned by someone else, and — the
one that actually matters — a **stale** marker over a working copy holding
foreign uncommitted work. A stale marker means "the last agent crashed *or* is
mid-thought"; uncommitted work in `@` means the difference is not knowable from
here, so it stops. `--refresh` bumps the timestamp and keeps the activity text.
`zenrelease --pause "<reason>"` leaves the marker as a note for the next agent
instead of deleting it. `zenmarkers --prune` lists leaked markers; `--prune
--yes` removes them.

Full-tree audit: 0.8 s.

### `zenfmt` — package-scoped formatting, and a diff classifier that explains itself

```
$ zenfmt                       # in zenmetrics
warn: 33 path dep(s) reach 20 dir(s) OUTSIDE this repo — `cargo fmt --all` would reformat them:
        /Users/lilith/work/zen/zenavif
        /Users/lilith/work/zen/zenjpeg/zenjpeg
        …
        /Users/lilith/zenavif   ← does not exist (broken path dep)
        this command passes -p per member instead, so they are untouched
REFUSED — zenmetrics has uncommitted changes: 1 file(s) modified in @: M crates/zenmetrics-cli/src/sweep/encode.rs
  CLAUDE.md: run cargo fmt on a CLEAN worktree and commit first.
  `zenfmt --classify` tells you whether that dirt is reflow or logic.
```

`--classify` reads the working-tree diff and says, hunk by hunk, whether it is
formatting or a real change — and *why*:

```
$ zenfmt --classify
REFLOW src/lib.rs:13   identical after whitespace + trailing-comma normalization — this is the
                       hunk a naive `diff -w` calls NON-whitespace and you call unsafe; it is rustfmt reflow
REFLOW src/lib.rs:17   identical after whitespace + trailing-comma normalization — …
LOGIC  src/lib.rs:21   differs after normalization:
        - pub const TILE: usize = 64;
        + pub const TILE: usize = 32;

3 hunk(s): 2 reflow (2 of them differ only by a trailing comma), 1 logic
VERDICT: contains real changes — this is intentional WIP. Do NOT launder it into a `style:` commit.
```

With no logic hunks it says `VERDICT: formatting only` and exits 0, which is
the CLAUDE.md gate for committing someone else's `cargo fmt` output as a
`style:` commit. A comment whose *text* changed is reported separately and
counted as logic, because it is.

`--check` runs a scoped `cargo fmt --check`; `-p <pkg>` narrows further.

### `zenspace` — reclaimable disk, minus anything in use

```
$ zenspace --need 70G --reclaim
50.1G free of 460.4G on /Users/lilith/work
50 target dirs ≥ 200.0M, 138.3G total

   32.8G  zen/jxl-encoder/target      SKIP: claimed by claude-T2-secant-guard 2m ago
    8.6G  zen/zenmetrics/target       idle 13h29m ← reclaim
    7.7G  zen/rav1d-safe/target       idle 1d ← reclaim
    5.7G  zen/zenbench/target         idle 1d ← reclaim
    …
need 19.9G more; selection frees 22.0G from 3 dir(s)

rm -rf /Users/lilith/work/zen/zenmetrics/target   # 8.6G
rm -rf /Users/lilith/work/zen/rav1d-safe/target   # 7.7G
rm -rf /Users/lilith/work/zen/zenbench/target   # 5.7G
re-run with --reclaim --yes to remove them
```

Two guards: a repo with a live `.workongoing` is never selected, and a target
touched within `--hot` minutes (default 20) is treated as an in-flight build.
Prints commands; only `--yes` deletes. Full scan: ~3.7 s.

## The traps these encode

Every one of these cost real time. The tools exist so they cost it once.

**A cancelled run is an absence of a verdict, not a pass.** Measured
cancellation rates on default branches: zenpipe 80%, zenmetrics/zensim/
zenanalyze 72%, zenavif 52%, zenjpeg 44%, zenwebp 20%. `zenci` renders
`CANCEL` as its own state and, when the newest run is cancelled, reports the
newest run that *did* carry a verdict. `zenred` skips cancelled runs entirely
when deciding whether a workflow is red, and when walking back for blame.

**A cancelled run can still contain a genuine failure.** Fail-fast cancels the
run once one job goes red. `zenci` peeks at the jobs of a cancelled run and
leads with `no verdict, BUT a job really failed: …` — the annotation goes
first precisely so a narrow terminal cannot truncate it away.

**The first failure is not the first line of output.** A red Lint fail-fasts
the matrix and leaves eight cancellations around it; the eye lands on those.
The real failure is the failed job with the *earliest* `completed_at`, which is
what gets reported. Cancelled jobs are counted in the tally (`3✗ 8✓ 4⊘`) and
never mistaken for the cause.

**The trunk name varies.** Most repos use `main`; **zenmetrics uses `master`**
and a server-side ruleset blocks creating `main`. Detection order:
`refs/remotes/origin/HEAD` → whichever of `main`/`master`/`trunk`/`develop`
exists as a remote-tracking ref → `gh repo view` → jj bookmarks. Cached for
seven days. Never assumed.

**`master@origin` is jj; `origin/master` is git — and git fails silently.**
`git show master@origin` writes its error to stderr and prints *nothing* to
stdout, so `git show … | sha256sum` cheerfully hashes the empty string. That
produced a false "these trees differ" verdict. Every revision argument goes
through `resolve_commit`, which translates the jj form with a warning, or dies
with both spellings printed. It never returns empty.

**`@` means different things to jj and to git.** To jj, `@` is the working-copy
change. To git, `@` is a plain alias for `HEAD`, which in a colocated repo is
`@-` — the *parent*. So `git rev-parse @` succeeds and silently answers the
wrong question. Anything `@`-shaped is resolved through `jj` first. This is
also why `git log -1` in a colocated repo looks like your commit is missing:
`zenverify` prints a note saying exactly that.

**The jj empty-commit trap.** Editing files *before* `jj new` snapshots them
into the previous change, so the change you then describe and push goes out
**empty**. It happened twice in one repo in one day — `682b266` in zenjxl and
`72bb4181` in jxl-encoder, both real, both zero files, both caught by
`zenverify` when pointed at them after the fact. Non-emptiness is a hard check.

**GitHub job logs are timestamp-prefixed and ANSI-coloured.** A line reads
`2026-08-29T19:48:54.4505924Z \x1b[1m\x1b[91merror\x1b[0m: using …`, so
`grep '^error'` matches nothing and you conclude the log is clean. Both are
stripped before matching. Trailing summary noise (`could not compile … due to
154 previous errors`, `Process completed with exit code 101`) is skipped
because it names no cause, and `warning:` lines are excluded outright — in a
broken build they outnumber the one line you want.

**Dependabot shatters into fake workflows.** Grouping runs by *name* turns each
update into its own pseudo-workflow (`cargo in /. for rand - Update
#1344031022`) with exactly one run and therefore no history — a dozen
permanently-red workflows that are neither. Grouping by `workflow_id` fixes it,
and runs GitHub generates itself (path `dynamic/…`) are hidden unless you pass
`--include-bots`. This alone cut `zenred` from 432 lines to 110.

**Blame needs the workflow's own history.** A repo-wide run feed gives an
infrequent workflow one or two entries, and "no green in the last 1 run" is not
blame. `zenred` re-queries per workflow for red ones. When there is still no
green in the window it says so instead of pointing at the oldest thing it
happened to see.

**`cargo fmt --all` follows path deps into sibling repos.** Confirmed: it
edited `../zenav1-aom`. From zenmetrics today, `--all` would reach **20
directories outside the repo**. `zenfmt` always passes `-p` per workspace
member and prints the list of dirs it just declined to touch. It also uses
`cargo metadata --frozen` first, so a status command cannot rewrite a foreign
`Cargo.lock` as a side effect.

**"Is this diff pure formatting?" is genuinely subtle.** rustfmt inserts a
trailing comma when it reflows a call onto multiple lines. A whitespace-only
comparison correctly reports that as non-whitespace, which reads as *unsafe*
unless you know the trick. `zenfmt --classify` normalizes whitespace *and* the
trailing comma, then names that as the reason — so the verdict is auditable
rather than a boolean you have to trust.

**Symlinks, worktrees and jj workspaces are normal here, not anomalies.**
`work/butteraugli` → `work/zen/butteraugli`, `work/zen/imageflow` →
`work/imageflow`; `rav1d-safe--census` is a linked git worktree (`.git` is a
*file*); `zenavif--encode-rd` is a jj workspace (`.jj`, no `.git`). Discovery
canonicalizes on realpath, prefers the real directory over the link, and folds
worktrees into their parent for CI purposes while still counting their `target`
dirs for `zenspace`. None of it is reported as a problem, every run.

**Archived repos and third-party forks.** `aom-decoder-rs` is archived, and
several repos are forks (`jxl-oxide`, `rust-rgb`, `dssim`, `jpegli`,
`image-tiff`). Nothing here writes to GitHub, so archiving is a non-event, and
non-owned repos are simply out of the default scope rather than flagged.

## Speed

These exist to shorten the loop, so they are measured. On this Mac, 73 repos:

| command | cold | warm |
|---|---|---|
| `zenmarkers` | 0.8 s | — |
| `zenspace` | 3.7 s | — |
| `zenci --fail-only` (all repos) | 16.5 s | 1.0 s |
| `zenred` (all repos, with logs) | 15 s | — |

`gh` calls run on a thread pool. Workflow-run lists are cached for 45 s
(`ZEN_RUNS_TTL`), which is short enough that a push-then-check loop still sees
reality; `--fresh` bypasses it. Trunk names are cached for a week. Job logs are
fetched only for workflows that are actually red, and only for the one job that
actually failed.

## Limitations, honestly

- `zenred`'s blame is *run-level*: it reports the head sha of the oldest
  consecutive failing run and the newest green one. If several commits landed
  between two runs, the culprit is somewhere in that range, not pinned.
- A workflow that has never been green in the fetched window gets an explicit
  "not blame, just the edge of the window" line rather than a guess.
- `zenci`/`zenred` only look at the trunk unless you pass `--branch`. PR runs
  are out of scope.
- `zenspace`'s "is a build running?" test is an mtime heuristic, not a lock
  check. It is conservative — it skips, it does not delete.
- `zenfmt --classify` is line-oriented, not a Rust parser. It will call a
  reordered-but-equivalent block "logic". That is the safe direction to err.

## Per-repo justfiles

These are **not** wired into the 56 per-repo justfiles — one wrapper line each
is worth adding by hand where it helps, rather than a scripted edit across 60
repos:

```make
# add to a repo's justfile if you want the local shorthand
ci:      ; zenci {{justfile_directory()}}
red:     ; zenred {{justfile_directory()}}
verify:  ; zenverify
fmt:     ; zenfmt
```

Note that many repos already define `ci:` and `fmt:` recipes with real content
— those should stay, and these should not overwrite them. The workspace-level
`justfile` already exposes `just ci`, `just red`, `just markers`, `just space`.

## Relationship to `cargo superwork`

`cargo superwork` (`dashboard`, `gh-dashboard`, `status`, `worktrees`) covers
the *ecosystem* view: crate versions, publish order, dependency graphs, PR and
issue lists, one ✅/❌ per repo. It is the right tool for "what is the state of
the release wave".

These are the *inner-loop* view: which workflow, which job, which error line,
which commit, is my push actually on the trunk. They deliberately do not
duplicate superwork's crate-graph work, and they need no compilation, so they
work on a remote box with nothing but Python and `gh`.
